Why Big data?
Think about how much data we create every day through our phones, applications, online purchases, smart devices, factory sensors, and business systems.
Across the world, we’re producing hundreds of millions of terabytes of data every day. Billions of connected devices are also generating data continuously, often in real time.

Slide3:what the term ‘Big Data’ actually means.”
“Now that we understand why it matters, let’s clarify what the term ‘Big Data’ actually means.”
It doesn’t simply mean having a very large file. Data becomes ‘big’ when our existing systems can no longer store, process, or analyse it efficiently enough for the required business outcome.
There are three simple ways to understand this slide.
The data might be too large for one machine. It might arrive too quickly for occasional batch processing. Or it might come in too many different formats, such as tables, JSON, text, images, and video.
In practice, we often experience all three challenges together.
Why does this matter? Because buying one increasingly powerful server is not a sustainable solution. Instead, we distribute the storage and processing across multiple resources.
This is the problem that modern platforms such as Databricks are designed to address.”
 
Slide4:
In this slide we will see the five v's of big data 
 
“A simple way to understand Big Data is through the five Vs shown here.
Firstly ,  we have Volume: how much data are we dealing with?
Next is Velocity: how quickly is that data arriving, and how soon we need to process it?
Then there is Variety. Data no longer comes only in neat tables. It can also be JSON, logs, text, images, audio, or video.
The fourth V is Veracity, which asks whether we can actually trust the data. Is it accurate, complete, and consistent, or does it contain errors and noise?
The final V is Value. Even if we have enormous amounts of fast-moving data, it is useful only when it helps us make decisions or achieve a meaningful result.
This slide matters because Big Data is not simply about size. It is about managing all five of these challenges together.”
 
Slide 5:conventional vsBig Data
 
“This slide compares conventional and Big Data processing approaches.
Conventional systems primarily process predictable, structured data using relational databases and predefined schemas.
Big Data systems support larger and more diverse datasets using distributed, parallel processing.
They are primarily designed to scale out across multiple resources and support flexible schema strategies.
The distinction is not absolute. Both approaches can use distributed infrastructure, schemas, and SQL.
The comparison explains why technologies such as Spark and the Databricks Lakehouse are used for modern data workloads.”

Slide 11: Lakehouse : Best of both worlds
 
“To understand Databricks, we first need to understand the Lakehouse.
A data warehouse is very good at organizing trusted, structured data for SQL, reporting, and dashboards. 
But it was not originally designed for every kind of raw data or machine-learning workload.
A data lake takes the opposite approach. It can store almost any data at a large scale and relatively low cost. 
But without good management, it can become difficult to trust, organize, and query.
The Lakehouse brings those two ideas together.
It keeps the flexibility and openness of a data lake while adding the reliability and management features we expect from a warehouse. Delta Lake helps provide capabilities such as ACID transactions, schema enforcement, and version history.
Why this slide is important?  engineers, and data scientists can work from a shared data foundation instead of constantly moving data between separate lake and warehouse platforms.”

Slide 16: How Apache spark runs a job 
 
“This slide shows what happens after we write Spark code.
First, we describe the transformations we want, such as filtering, joining, or grouping data. 
Spark usually waits until we request an actual result before it begins the work.
The driver then looks at the complete request and builds an execution plan. It breaks that plan into stages and smaller tasks.
The cluster manager provides the computing resources, 
and executor processes it and run on the worker machines. 
The driver sends tasks to those executors, 
which process those different data partitions at the same time.
The output might appear in our notebook, return as a small result, or be written to a Delta table.
Why is this important? Spark becomes powerful by dividing a large problem into smaller pieces that can run in parallel. But simply adding more executors is not always enough; the data and workload must also be organized for effective parallel processing.”
In Databricks:
1. You write Python, SQL, Scala, or R code in a notebook.
2. The Spark driver creates an execution plan.
3. Spark divides the data into partitions.
4. Workers process the partitions in parallel.
5. The output is displayed or written to a table.
 
 
 
Slide 17: Delta lake : reliability on the data lake 
 
“A regular data lake can contain many files, but files alone do not automatically behave like a reliable database table. Delta Lake helps solve that problem.
The actual records are stored mainly in Parquet files. 
Delta Lake then adds the _delta_log, 
which keeps track of valid files, table structure, and committed changes.
This log gives us several useful capabilities.
Transactions ensure users do not see half-completed updates. 
Time travel lets us inspect earlier table versions, as long as the required history is still retained.
Schema enforcement helps stop incorrectly structured data from entering the table. 
When the structure genuinely needs to change, schema evolution provides a controlled way to update it.
The same table can also support both scheduled batch processing and continuous streaming.
Why is this important? Delta Lake keeps the flexibility of cloud storage while making the data more reliable and manageable.”
 
Slide 18: clusters : the engines you turn on and off 
 
“This slide explains Databricks compute options available to us .
“This slide explains where the actual processing power in Databricks comes from.
For exploration and development, we can use interactive compute. We start it, connect a notebook, test code, 
and continue using it while we work. 
Auto-termination can be switched off after a period of inactivity.
For scheduled pipelines, job compute is usually a better fit. 
Databricks starts the resources for the job run and shuts them down when the run is complete.
Autoscaling allows classic compute to move between a minimum and maximum number of workers. 
It can add capacity during demanding periods and remove workers when less capacity is needed.
We can also choose between classic and serverless compute. 
Classic gives us more control over infrastructure. 
Serverless removes much of that management because Databricks provisions and scales the resources.
Why does this matter? The best compute choice depends on whether the workload is interactive, scheduled, highly customized, or designed for minimal infrastructure management.”

“This slide puts everything we’ve discussed into one picture.
