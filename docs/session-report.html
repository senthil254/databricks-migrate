    The 3 warnings hide a real defect
    sql — input
    e.payload:user.id::STRING AS user_id
    sql — broken output
    CAST(e.payload/* SESSION_USER() */.id AS VARCHAR(16777216)) AS user_id
-- FIXME: Unsupported expression in a JSON path

    The JSON path key user was parsed as Snowflake's USER session function and replaced with a comment — producing structurally broken SQL, emitted only as a warning.

    Isolated with a controlled probe

    sql — probe
    SELECT
  e.payload:user.id::STRING     AS a_user,
  e.payload:customer.id::STRING AS b_customer,
  e.payload:table.id::STRING    AS c_table,
  e.payload:device.id::STRING   AS d_device
FROM raw.events e;
    KeyResult
    :userBroken
    :customerCorrect
    :table (reserved word)Correct
    :deviceCorrect

    Since :table — itself a reserved word — transpiles fine, this is not general reserved-word handling. It is specific to the USER function collision.

    Workaround: bracket-quote the key in the source (e.payload['user'].id), or grep the output for SESSION_USER() and fix those sites by hand.

    Does this need a new workspace? No — twice over

    Not possible: no account-console API on this tier.

    Not useful either: Unity Catalog allows one metastore per region per account, and catalogs live in the metastore. A second workspace in the same region attaches to the same metastore and sees the same catalogs.

    The catalog is the isolation boundary, not the workspace. A workspace is a new office building; a catalog is a new filing cabinet. If you want your files separate, you need a cabinet — a different building doesn't help when everyone shares the filing room.

    REST API cannot create catalogs here — SQL can

    Problem 1The Analyzer refused to start

    This was the biggest problem of the day.

    Modern Macs use a different type of chip than older Macs did. Software built for the old chip won't run on the new one — unless you install a translator called Rosetta 2.

    Lakebridge's Analyzer was built only for the old chip. This Mac has the new one and didn't have Rosetta 2. So the Analyzer simply could not start.

    How we proved it, rather than guessing

    We askedAnswer
    What type of program is the Analyzer?Intel only
    What chip does this Mac have?Apple Silicon
    Is Rosetta 2 installed?No

    Three checks, one clear answer. The fix took one command. During the install a scary-looking "Package Authoring Error" appeared — it's a harmless cosmetic complaint inside Apple's own installer. The line that mattered read finished successfully.

    This is not your fault or a setup mistake. It's an oversight by whoever packaged Lakebridge. Anyone with a modern Mac will hit it.

    Problem 2One word breaks the translator

    In one file Lakebridge produced broken output. The original meant "get the user's ID". Lakebridge mistook the word user for a special command and replaced it with a note-to-self instead of translating it.

    Why this is dangerous: Lakebridge marked it only as a warning, not an error. If nobody reads the warnings, broken code reaches production and fails later.

    We proved exactly what causes it

    Rather than guess, we ran four almost-identical lines, changing only one word:

    Word usedDid it break?
    userBroke
    customerFine
    tableFine
    deviceFine

    Only user breaks it — even table, also a special word, works fine. What to do: if your data uses "user" as a label, check those lines by hand after translating.

    QuestionDo I need a new workspace?

    No — for two separate reasons. First, this type of account doesn't allow creating them. Second, and more surprising: it wouldn't help anyway.

    Databricks stores your data organisation in one shared place per region. A new workspace would connect to that same shared place and see exactly the same data.

    A workspace is like a new office building. A catalog is like a new filing cabinet. If you want your files kept separate, you need a new cabinet — moving buildings doesn't help, because everyone still shares the same filing room.

    FilesExcel doesn't work directly

    FormatWorked?What happened
    CSV (plain text spreadsheet)Yes20 rows loaded immediately
    Parquet (compressed data file)Yes50 rows loaded immediately
    Excel (.xlsx)NoDatabricks cannot open Excel files at all

    The fix is to convert Excel into a format Databricks understands first. Not difficult, but it must be built into your process — Databricks won't do it for you.

    The main eventBreaking things on purpose

    Anyone can run a checking tool against two identical tables and get "everything matches". That proves nothing — a broken tool gives the same answer.

    So we deliberately damaged a copy of the data in four ways, then asked the Reconciler to find them without telling it what we'd done:

    What we brokeFound it?
    Changed one customer's nameYes
    Changed one customer's region to "ANTARCTICA"Yes
    Added 999.99 to one customer's balanceYes
    Deleted one customer entirelyYes

    Four faults planted. Four faults found. Nothing missed, nothing wrongly flagged. It took about 31 seconds. This is the result that matters — it proves the tool genuinely does its job.

    VerdictSix things to remember

    1. On a modern Mac, install Rosetta 2 first. Otherwise the Analyzer won't start and the error won't tell you why.
    2. Check anything containing the word "user" by hand after translating.
    3. Excel files need converting first. Build it into your process.
    4. You don't need a new workspace. A new catalog gives the separation you want, in minutes.
    5. On accounts without clusters, the checking tool needs manual setup. It works — it just isn't automatic.
    6. Always test a checking tool by breaking something on purpose. If it doesn't notice, it isn't protecting you.

    Bottom line: Lakebridge works and is worth using. Two rough edges exist, both have workarounds, and both are now documented.
